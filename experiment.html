01 · Model & harness comparison

A controlled experiment from an earlier phase asked a question with a real budget implication: can a cheaper model helped by automated quality gates match a stronger model with no gates — and cost less? This entry is the short version. The full deep-dive lives in the project's own documents.

Scope & caveat

This experiment ran in the earlier phase, on the first backend (TypeScript / NestJS), before the greenfield restart described in the rest of this wiki (whose backend is Java / Spring). Cost figures are approximate, captured with external tooling — good for ranking the arms against each other, not for billing. Every claim is "for this use case, at this stage."

The setup

One representative feature — incident CRUD — was built several ways from an identical starting point, with identical after-the-fact quality checks on every arm. The variables: which model plans, which model implements, and whether the deterministic sensors run inside the build loop or only afterward.

ArmPlanImplementGate in loopResult
A1OpusSonnetNo4/6 clean · ~$4.12 · <1 hr
B2SonnetHaikuYes6/6 clean · ~$7.66 · ~2 hrs
CSonnetSonnet + HaikuYes + 1 rule6/6 clean · ~$4.03 · ~45 min

"Clean" = how many of six deterministic sensors pass. 6/6 means no hygiene debt; 4/6 means working code that still leaves maintainability debt for someone to service later.

The headlines

  • The cheap tier was not cheaper. The all-Haiku arm (B2) was the most expensive implementation of the three — it needed more attempts, redo cycles, and correction loops to reach the same finish line. Price per token is not price per result.
  • The cheap-model experience was worse. It took roughly twice the wall-clock, ignored explicit written spec decisions, and twice reported failing work as "done" — caught only by independently re-running the checks. That human re-verification is a real cost that never shows in a token bill.
  • What actually improved quality was the gate, and it is model-agnostic. The strong-model arm was already 4/6 clean with no gate; the jump to 6/6 came from the in-loop sensor gate plus one encoded convention — which helps the strong model exactly as much. So the gate does not create a case for cheap models; if anything it removes one.
  • Cost is not the bottleneck. Implementation was about $4 per feature; the dominant cost is the human-in-the-loop work around it — planning, coordinating, re-verifying — which the model tier does not change.
  • Where routing paid: keep the strong model on the hard, structure-defining slice. Routing the easy, derivative slices to the cheap model saved only a couple of dollars against added coordination and risk — marginal at this scale.
The one-line takeaway

For this use case, at this stage, there is no case for lower-tier models: the cheap tier was slower and not cheaper, even with a quality gate around it — and because that gate is model-agnostic, it helps the strong models just as much, leaving the cheap tier no advantage to offer. A "not yet," not a "never": the door reopens as the codebase matures and enough conventions can be encoded to make the cheap tier safe.

The recommendation it produced

  • Plan with the strong model where the design is genuinely open; use a cheaper planner where the contract is already pinned (don't pay for reasoning on transcription-grade CRUD).
  • Implement with the mid tier for now, and set the cheapest tier aside for this kind of work until conventions mature.
  • Keep investing in the harness — the cheap, deterministic, model-agnostic layer that actually moved quality.
  • Keep the strong model on structure-defining slices — the one routing rule that clearly paid.

Where the full detail lives

This entry intentionally omits the arm-by-arm cost derivations, the tooling-bug confound that inflated one arm, and the full cross-arm analysis. Those live in the project's deep-dive documents, kept outside this wiki:

  • model-and-harness-comparison.md — the full report and every caveat.
  • model-comparison-presentation-script.md — the slide-by-slide walkthrough for a management audience.

02 · Generating a whole test suite (run 2)

A later, independent experiment in the QA repo asked the same tier question of a different task: not building a feature, but generating a Playwright UI suite. Three models wrote a suite for the Dispatcher console from byte-identical inputs — the same DOM.md, the same app checkout, the same prompt, a 10,000-token thinking budget for all three. Model id was the only variable.

Measurehaikusonnetopus
Wall clock6m 38s32m 48s36m 36s
Cost$0.56$8.52$12.66
Designed cases → tests66 → 8836 → 4352 → 63
Ran its own suite?NoYes · 3×Yes · 2×
Runnable as deliveredDOAYesYes
Cost per passing testn/a$0.20$0.20
  • Best compromise: sonnet. A third cheaper and four minutes faster than opus at an identical cost-per-passing-test. It ran its own suite three times and fixed three real bugs in its first draft. What you give up is breadth (no pagination, deep-link or resilience coverage).
  • Highest quality: opus. Best Page Object discipline, real traceability tags, table-driven boundary coverage, stubbed error/empty states — worth the extra ~$4 when the suite is a long-lived asset.
  • haiku was not a cheap alternative — it was no alternative. On paper the best value (most cases, 15× cheaper, 5× faster); in practice it never ran what it wrote, and the suite could not execute at all — a fixture built its context without the base URL, so the first navigation of nearly every test threw. Behind that, a dozen tests carried no assertion. Usable for test design, not for test binding.
The run-2 takeaway

The single largest quality signal was simply whether the model ran its own suite — it separated the two usable suites from the unusable one, and no static metric predicted it. The generation lane echoes the delivery finding: price per token is not price per result, and the cheapest tier's unverified "done" is the expensive part.

This comparison and the QA pipeline that hosted it are detailed on the QA automation page.

03 · Condensing the documentation layer

The first two entries measured what the harness produces as code. This one measures what it produces as prose. In one month the repository accumulated 20 architecture decision records and roughly 5,500 lines of comment over roughly 33,000 lines of code. The team's judgement was that this is too much. The question is whether that volume is the harness working as intended, or a rule shape that manufactures documentation nobody reads — and what it costs to take it back out.

Status

first readout  The intervention merged between 4 and 7 Sep 2026 (#321, #323–#332), so the volume measures below now carry real numbers instead of the baseline alone. The entry stays open on the one measure that matters — whether comprehension held — and the first two weeks of delivery after it have already produced a signal worth recording: the comments are growing back.

The baseline

Measured across the repository one month after the greenfield restart, on the current stack (backend in Java / Spring).

SurfaceBaseline
Architecture decision records20 documents · 1,858 lines · ~93 lines each
backend/~3,102 comment lines over ~14,500 — 21%
dispatcher-app/13% comment lines
infra/25% comment lines — the densest area
package-info.java70 files · 456 comment lines, every one written by mandate
Whole repository~5,500 comment lines over ~33,000 lines of code

The diagnosis

The cause is not a missing rule. It is the shape of the rules already in place — each one, read by an agent that wants to comply, reads as an instruction to write:

  • A rule that enumerates admitted genres is a licence. The comment rule named four legitimate genres; naming them made a comment that fits one feel earned rather than justified.
  • The reversal test admits almost everything. "Would a future reader need to know why this was chosen?" passes any deliberate choice, and every choice in a plan is deliberate.
  • An empty box in a template gets filled. The tech-plan template's Key decisions table carried an ADR column — a structural invitation to write one ADR per decision, which is the mechanism behind the count.
  • A mandate produces volume, not value. The backend rule required a why-javadoc in every package-info.java: 456 lines that existed because they were required, not because a reader was stuck.

The intervention

  • Both rules collapse to one sentence each in CLAUDE.md, and the two rule files are deleted — a single negative criterion in place of an enumeration of admitted genres.
  • The ADR column comes out of the tech-plan template, and the why-javadoc mandate out of the backend rule.
  • Five ADRs are written from scratch to replace the 20, one page at most each, absorbing only the decisions that still bind. Numbering restarts; nothing external cites the old series.
  • Each area is then swept in its own pull request, largest first — backend/, dispatcher-app/, volunteer-app/, infra/ — so a red build localises to one area.
  • Three carve-outs survive on purpose: the backend's port javadoc (the specification both adapters are tested against), the architecture test's per-exception reasons (the entire value of that check), and the OpenAPI contract, left for the next session that opens it rather than granted a written exception.

Re-measured on one footing at three points in history — every hand-written Java and TypeScript file under backend/src and both apps' src, blank lines and the generated schema.d.ts excluded — so the three rows are comparable to each other rather than to the baseline table above, which was counted on a wider footing. infra/ is counted separately below, with its own file types.

Per area, before against after the sweep against today: backend/src 23.9% → 4.0% → 8.2%; dispatcher-app/src 15.2% → 5.8% → 5.5%; volunteer-app/src 12.7% → 2.7% → 3.7%; infra/ 26.4% → 14.8% → 19.2%.

  • The intervention worked, and by a wide margin. 4,868 comment lines became 949 — −80.5%, density 19.3% → 4.5% — and the twenty ADRs became five, 1,858 lines → 364, −80%. Two thirds of the files stopped carrying any comment at all.
  • It did not hold. In the 50 commits of delivery that followed, comments grew back +91.8% (949 → 1,820 lines), taking density from 4.5% to 6.7% — +2.2pp, a 49% relative rise in four days.
  • Comments are growing ~3.2× faster than the code. Source grew 28.7% over the same window against the comments' 91.8%, so 14.4% of every net line added since the sweep has been a comment — three times the density the sweep left behind. At this rate the pre-rule 19.3% returns in roughly two months of delivery at the same pace.
  • The regrowth is not uniform. The backend doubled (4.0% → 8.2%) and infra/ climbed back to 19.2%, while the dispatcher app held flat (5.8% → 5.5%) — the areas that see the most agent-written code are the ones that drift.

The follow-up: what each model writes now

To separate the rule from the author, one small self-contained feature — a CSV export of every incident — was built three times from the byte-identical commit on main: once by sonnet, once by opus, once by a human developer as the baseline. Same repository, same one-line rule, model id and author the only variable.

  • opus comments roughly 4.6× more densely than sonnet — 8.3% against 1.8% of added lines, 10 comment blocks against 2, on the same feature under the same rule. It is also the density driving the 8.2% the backend has drifted back to.
  • The restraint rule holds far better for sonnet. Both of its comments are the cases the rule is written for: the ordering guarantee a port method makes to its callers, and the reason behind the RFC 4180 escaping. It left the tests uncommented entirely.
  • opus overshoots mainly in the tests. 10 of its 27 comment lines document test methods whose names and bodies already say the same thing. Its production comments are more defensible — one explains that Spring matches a literal path segment ahead of a template one, which the code genuinely cannot show.
  • The human wrote no code comment at all, and expressed the endpoint's intent only where this repository does want prose: the contract description — one line, where opus wrote about six per endpoint.
  • A written rule bends the volume, it does not set it. The same one-line instruction produced 0%, 1.8% and 8.3% across three authors. On comment discipline the author, not the rule, is the dominant variable — which is the same shape entry 01 found for quality: what held was the gate in the loop, not the prose.
What would falsify it

A swept comment that has to come back, or an agent that misreads code the deleted comment used to explain. The first three measures are deterministic and settled within the stack; the fourth is the one that matters and only shows up over the following weeks, which is why this entry stays open after the pull requests merged. The fifth has already answered in the other direction: the volume is coming back, so the next thing this entry has to test is a sensor — a density check in the build loop — rather than another sweep.
