04 · QA automation

The QA lane — a test factory built from skills

Testing runs as its own instrumented pipeline, in its own repository, alongside the delivery work. The same principle carries over: take everything a machine can decide and let a machine decide it. Here that means test authoring itself is an agent chain — inspect the app, design cases, bind them to code — gated by a human review in the middle and by deterministic checks around the edges.

What this is

A central QA repository (cpr-dispatcher-test) holds the committed Playwright suites and runs them as a regression gate on the product monorepo. A separate Claude Code plugin (xplorebe-qa-skills) holds the fourteen skills that write those suites. The tests are an output; the reusable asset is the skill chain that produces them.

Two jobs, deliberately kept apart

The QA repo does two things, and the split between them is the point: one is automatic and cheap, the other is manual and deliberate.

Automatic · every PR

Regression gate

A PR or a merge in the product monorepo fires a repository_dispatch per affected target (dispatcher UI, volunteer UI, API). The QA repo runs the already committed suite for that target — smoke on a PR, full regression on a merge. No test generation, no model in the loop.

Manual · on demand

Test authoring

Generating or refreshing tests is workflow_dispatch only — a person picks a target, a model, an effort level and a spec style, and the skill chain runs and opens a PR for review. Never a side effect of someone pushing code.

Why the separation

Generation is where the cost and the risk live — a model reading the app and writing code. Making it a deliberate, human-started call keeps it out of the hot path, while the committed suites still gate every product change for free. The two never share a trigger.

Two lanes, mirror images of each other

Every stage exists twice — once for the browser (UI lane) and once for the service contract (API lane) — with the same shape at each step. The UI lane crawls the app to a shared DOM.md; the API lane parses the OpenAPI spec to a shared API.md. From there the chain is identical:

[chain] inspect → design → review → bind → run → heal → trace
inspect ui-inspector → DOM.md · api-inspector → API.md
design spec-to-cases → test-cases.md + glossary + traceability
▸ HUMAN REVIEW GATE cases signed off before any code is written
bind test-writer → Playwright code + Page/Service objects + CI
run test-healer → classify drift vs. assertion vs. real bug
heal fix fragility in Page/Service objects; quarantine @flaky
trace traceability-auditor → gh issues vs. @issue-N tags
design and binding are different jobs with different review gates.

The split between designing cases and binding them to selectors and routes is load-bearing: they are different jobs, so they get different review gates. A human reviews the reasoning (the cases) before any effort goes into the mechanics (the code) — the expensive rework of wiring the wrong tests is caught before it happens.

Plain code by default, Gherkin on request

Each lane has two output formats. The default is plain Playwright Test (describe/test); saying "use Gherkin" opts into Cucumber .feature files plus step definitions. The design skills produce the same reviewable cases either way — only the binder differs. Selectors and interactions live in Page Objects (UI) and Service Objects (API), never inline in a test.

The fourteen skills

Packaged as a single Claude Code plugin, installed once and shared across every project. No org or repo names are baked in — each skill takes its target as input.

Design decisions worth keeping

  • test.fail() is the marker — nothing beside it. A case for behaviour the app does not have yet carries test.fail() with the ticket in its reason; its expected red counts as a pass, and the day the defect is fixed the run goes red with "Expected to fail, but passed" — forcing the marker to be removed instead of drifting out of date. There is deliberately no parallel @known-gap tag: a second thing to keep in sync is the half that goes stale, because nothing fails when a tag outlives its gap.
  • The suite cleans up after itself. The dispatcher app writes to a real, shared backend with no reset. Each test cancels the records it created; a teardown project then deletes every incident carrying one of the suite's title markers — clearing other runs' litter too, which is the point.
  • Git hooks that install themselves. npm ci points git at .githooks/ via the prepare script — no husky, no extra dependency. Pre-commit formats staged files; pre-push mirrors CI's format gate so a green push means a green check.
  • One installed copy of the skills, one owner. The skills are a plugin, not a checked-in copy and never a personal symlink — a personal-scope copy shadows every other on a name collision, so a stale clone wins silently. (Not hypothetical: a clone four commits behind once served outdated bugs-reporter guidance.) CI has no plugin step, so it stages the skills from the pinned repo instead. The same "one home per fact" discipline as the delivery harness.

QA findings

What held up

Test authoring splits cleanly into a reasoning step and a mechanics step. Gating the designed cases with a human before a line of test code is written is the same move as gating each delivery slice: it keeps the expensive rework — binding the wrong tests — from ever starting.

  • The biggest quality signal was simply whether the model ran its own suite. No static metric predicted it — see the second model comparison below.
  • Markers must be self-invalidating. A convention that can silently outlive what it described (a stale gap tag) is a convention that will. Prefer the form that goes red on its own when it drifts.
  • Automatic and deliberate work want different triggers. The cheap, model-free regression gate runs on every change; the expensive, model-driven authoring runs only when a person asks.

The model comparison this repo produced

The QA repo hosted a second controlled model experiment — three tiers generating the same UI suite from byte-identical inputs. Its sharpest finding (the cheapest tier wrote a suite it never ran, and it was dead on arrival) is summarized on the experiment reference as run 2.
