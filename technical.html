01 · Technical track

The harness, and how the pipeline earned trust

The recurring technical thread across the three weeks is a single move: take everything a machine can decide, and let a machine decide it — deterministically, cheaply, and before a human ever reads the diff. What is left for people and for the model is the judgement only they can supply.

The harness model

We treat the harness as everything around the model: the controls that steer an agent before it acts, and the controls that check the result after it acts.

  • Guides steer the agent before it acts — skills, specs, CLAUDE.md constraints, the pinned contract.
  • Sensors check the result after it acts — type checks, linters, architecture rules, duplication and dead-code detectors, tests.
The economic principle

Prefer computational work (CPU: deterministic, effectively free, repeatable) over inferential work (the model: probabilistic, costs tokens, varies per run). Wherever a quality property can be checked by a deterministic tool, push it onto the CPU and save the model budget for design and implementation.

Executable conventions beat prose conventions

A convention written only in prose can be skipped by a weak follower — human or model. The durable form of a convention is an executable check. The clearest evidence came from the earlier experiment: a documented rule ("persist through the repository, not raw SQL") was ignored by the cheap model until it became a lint rule — after which the same deviation simply could not be merged. Every sensor that exists is a convention the model can no longer ignore.

Finding

The reusable, model-agnostic quality win is the in-loop sensor gate plus conventions encoded as checks — not the choice of model. A rule, once it exists, binds every model equally.

Review moved into CI (week 2)

In week 1, review ran from our own terminals. In week 2 it moved into GitHub Actions: opening a pull request fires a review workflow that invokes the repo's own review skill, and findings land as inline comments on the diff. The implementing agent then waits for that feedback and fixes it inside the same slice, before the next slice starts.

Three details are load-bearing:

  • It runs the stronger model explicitly. The action's default is a cheaper model; that is not what we want reviewing a slice.
  • It reviews against the pull request's base branch, not main. Because we stack pull requests, a diff against main would re-flag work already reviewed in a lower layer.
  • It runs once. The workflow counts existing review comments and stops if it finds any; re-reviews are on-demand from a local session.
Observation — how many review passes?

On one slice we fixed the first review's findings, then deliberately ran review a second time expecting it to be clean. It found more. We fixed those, ran a third pass, and that was clean. So one pass is a choice, not a finding: a second pass demonstrably finds real defects. We run one anyway, because a second pass on every pull request is a cost we could not yet see.

Determinism instead of judgment (week 2)

The week-1 bottleneck was review. The week-2 answer was to stop asking any reviewer — human or model — to decide anything a machine can decide.

Plan-as-state and resumability

The plan for a feature is not a document or a conversation — it is a tracker issue broken into sub-issues, one per slice, each naming its own base branch. That is what makes handoff work: if one person stops mid-stack, the next reads the plan issue and the merge state and knows exactly which slice is next. The strongest single claim from week 1 was that the process is resumable by a different person — no verbal handover, no stale document to reconcile.

One slice, one pull request

A week-1 failure taught the rule. The orchestrator delegated slices to subagents and then started repairing their work — and because we stack pull requests, those repairs landed in the wrong slice (a defect surfaced in one layer got fixed several layers up). The fix was a rule: the orchestrator does not write code, and the loop is implement slice → review slice → then the next slice. A finding in a layer can only be repaired in that layer, because the layer above does not exist yet.

Keeping context clean

Two week-2 disciplines target the fact that everything the model reads is input:

  • A comments rule. The model wrote documentation-style comments in code. We restricted code comments to four genres — a local constraint, an operational trap, a decision citation, an external workaround — and removed anything else, applying the rule backwards to the whole repository in one commit.
  • One home per fact. Before a fact is written anywhere, three tests: does it deserve to exist (what a reader can derive from the code stays undocumented); when is it needed (that picks the surface — an always-loaded file, a path-scoped rule, a skill, or a README); and may a second copy exist (only when load-bearing, otherwise a link).

Technical findings

What held up

Deterministic sensors are the cheap, model-agnostic quality lever. Inference is strong at behaviour (high coverage, passing tests) and weak at hygiene (duplication, dead code, complexity); cheap CPU checks catch the hygiene the model misses, for near-zero marginal cost.

  • Encode conventions or lose them. A prose rule a weak follower can skip becomes binding the moment it is a check.
  • Move review into the loop, per slice. Gating each slice before the next keeps fixes in the layer that owns them.
  • Plan-as-state makes work resumable and reviewable in minutes.
  • Two things sensors can't catch still need a human or a targeted test: a model reporting unfinished work as "done", and byte-exact behavioural-contract details.

The earlier controlled comparison behind several of these claims — model tiers versus harness configuration — is summarized in the experiment reference.
